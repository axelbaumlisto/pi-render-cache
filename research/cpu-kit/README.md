# Почему pi ест ядро: набор для замеров

Задача агенту: **найти, на что уходит процессорное время pi в рабочей сессии,
и предложить исправление, подтверждённое замером.**

Не читать исходники вместо замеров. Здесь уже есть случай, когда чтение кода
дало неверный ответ: в бандле видно, что `AssistantMessageComponent.updateContent()`
пересобирает `Markdown` на каждое обновление, а замер работающей программы
показывает, что при стриминге `Markdown` не создаётся ни разу.

## Как запускать

```bash
./run.sh frames "" 45 stream                    # новая сессия, поток ответа
./run.sh classes "$(ls -S ~/.pi/agent/sessions/*/*.jsonl | head -1)" 60 mixed
./collect.sh 3 45                               # вся матрица, результат в results/<дата>/
```

Зонды — это расширения pi, которые запускаются через `pi -e` и пишут JSON:

| зонд | что меряет |
|---|---|
| `frames` | число кадров, мс на кадр, доля перебора строк на картинки, ЦПУ, память |
| `classes` | своё время каждого класса компонента (без вложенных вызовов) |
| `children` | из каких компонентов собран экран |
| `segmenter` | вызовы `Intl.Segmenter.segment`, символы, время |
| `triggers` | кто просит перерисовку (таймеры, ввод, поток) |

Сценарии: `idle`, `scroll` (листание истории), `stream` (вопрос модели), `mixed`.

## Правила замера (на них уже обожглись)

1. **Настоящий терминал.** Всё запускается через `script` с размером окна
   50×160. При 80×24 буфер ~29–40 строк и любая проблема выглядит дешёвой.
2. **Свой патч не считать доказательством.** Расширение, проверяющее само
   себя, даёт красивые цифры ни о чём: отфильтровывайте вызовы из своего кода
   по стеку (`canaryVerify` и подобное).
3. **Убирать конкурентов.** Если в `~/.pi/agent/settings.json` стоит
   `pi-render-cache`, он патчит те же методы — замер сорвётся. Временно убрать.
4. **Не верить одному прогону.** Кадровые замеры в живой сессии гуляют от 10 до
   124 мс на кадр. Нужна медиана нескольких прогонов либо детерминированный
   прогон на живых классах.
5. **`pi -ne` не годится для сценариев с моделью** — без расширений нет
   моделей, сессия просто стоит и ничего не рисует.

## Что уже установлено (не переоткрывать)

Замерено на выпущенном pi 1.0.2, Apple M3, Node 22.23.

- **Рендерер вшит в бандл.** С 0.84.3 пакет `@earendil-works/pi-tui` рядом с pi
  не грузится. Патчить надо модуль из `dist/bundle/chunks/*.js`, найденный по
  экспортам (имя чанка — хеш содержимого, меняется каждый релиз). См.
  `probes/resolve.mjs`.
- **Поток ответа не идёт через `Markdown`.** Патч `addChild` у всех контейнеров:
  экран собран из `ExpandableText`, `Container`, `Spacer`; объектов `Markdown`
  создано ноль, вызовов отрисовки ноль. `ExpandableText` наследует обычный текст.
- **У pi есть свой кеш отрисовки:** `renderCached(context, component, width)`
  плюс память последней отрисовки у каждого объекта. Внешний кеш разметки
  получает ноль попаданий: четыре сессии (240, 98, 85, 76 МБ), с листанием и
  стримингом — 222 промаха, 0 попаданий.
- **Кеш разметки на 1.x вреден.** Одинаковая работа, живые классы, 6600 строк,
  5 прогонов, медианы: без патчей 87.3 мс, кеш сегментов 81.3 мс (1.07×), кеш
  разметки 104.7 мс (0.83×), оба 99.2 мс (0.88×). И это при 240 попаданиях из
  360: построение ключа дороже самой отрисовки.
- **Сегментация ещё даёт выигрыш** — 1.07×, попадания есть.
- **Новая сессия со стримингом почти ничего не стоит:** кадр ~1.2 мс, за всю
  сессию 9 кадров. Цена появляется в больших возобновлённых сессиях: 10–28 мс
  на кадр, а в одном прогоне кадр стоил 124 мс.
- **Перебор строк на картинки** (`parseKittyImageHeader`, `isImageLine`) — от 3
  до 5% времени кадра в скриптуемых прогонах. В профиле настоящей шестичасовой
  сессии он занимал 40% занятого времени процесса — воспроизвести по команде не
  удалось.

## Первые цифры этим набором (большая сессия 240 МБ, листание + поток)

```
frames      кадров 4, 31.27 мс/кадр, картинки 0.9% кадра, ЦПУ 1.6 с, память 807 МБ
classes     Container 137.3 мс/2758 вызовов | Markdown 83.0 мс/684 | Text 30.5 мс/1128 | Box 12.5 мс/627
children    Box <- MouseRegion x195 | Container <- Spacer x174 | Container <- Container x53 | Container <- Markdown x51
segmenter   вызовов 1878, символов 133940, 17.3 мс
triggers    processTicksAndRejections x15, listOnTimeout x5
```

Отсюда сразу видно, куда копать: **2758 вызовов отрисовки контейнеров** и 1128
текстов на четыре кадра — дерево перерисовывается целиком, а не видимой частью.
И история (в отличие от потока) всё же идёт через `Markdown` — 51 штука.

## Открытые вопросы (то, ради чего всё это)

1. **Почему в настоящей рабочей сессии кадров в десятки раз больше, чем в
   скриптуемой?** В скрипте 3–9 кадров за минуту, у человека — сотни. Найти, кто
   их заказывает: зонд `triggers`, плюс искать анимацию индикатора (в issue
   #6665 упоминают перерисовку раз в 80 мс) и обновление счётчика времени раз в
   секунду.
2. **Почему кадр в большой сессии стоит 10–28 мс?** Разложить `doRender` на
   составляющие: отрисовка дерева компонентов, склейка строк, сравнение с
   предыдущим кадром, запись в терминал. Зонд `classes` даёт только первую часть.
3. **Масштабируется ли цена кадра от размера истории?** Если да — виновата
   отрисовка всего дерева вместо видимой области. Это проверяется сравнением
   сессий разного размера (240 / 98 / 85 / 76 МБ) при одинаковом сценарии.
4. **Сколько стоит `compositeTuiLine`?** В issue #6665 участник намерил 38.8% →
   16.1% на полноэкранном режиме. В обычной сессии альтернативный экран не
   используется вовсе — проверить, где он включается и важно ли это.
5. **Воспроизводится ли профиль настоящей сессии** (17.1% ядра, из них 40% на
   переборе строк)? Нужен сценарий, который это даёт по команде.

## Исходный upstream-контекст

Issue: https://github.com/earendil-works/pi/issues/6665 — открыт, назначен, в
работе. Две заявленные причины: несохранённая сегментация графем и пересборка
markdown на каждый чанк. Вторая на 1.0.2 уже не действует (см. выше). В
комментариях есть третья: пересборка строк при компоновке кадра.

## Что считать результатом

Не «я посмотрел код и думаю». Результат — это:

- замер до и после на одном и том же сценарии, с медианой нескольких прогонов;
- объяснение, какая строка кода даёт разницу;
- честно названное, что проверить не удалось.
