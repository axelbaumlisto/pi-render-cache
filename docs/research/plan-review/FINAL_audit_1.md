## 1. Errors

No blocking correctness errors found in the integration seams. Two low-severity findings:

- **Low — `src/md-cache.js:293` misleading comment.** `origHash: hashString(orig.toString()), // version-drift guard (checked by the extension)`. Nothing reads `state.origHash` outside test files (`tests/md-cache.test.js:606`, `tests/extension.test.js:97,102`, which only assert it is stored and stable). The actual "version-drift guard" that gates installation is `evaluateMdSupport()` in `src/patch-state.js:74-99`, which independently recomputes `hashString(current.toString())` against the allowlist *before* calling `install()`. `origHash` is therefore write-only production code (test-only consumer), not "checked by the extension" as the comment claims. Not a functional bug — the real gate works — but the comment overstates what the field does and could mislead a future maintainer into thinking removing it is safe-but-untested, or into thinking there's a second runtime check that doesn't exist. Recommend either wiring `origHash` into `/rcstats`/`evaluateMdSupport` reuse, or fixing the comment to say "recorded for test/diagnostic use only."

- **Low — `src/md-cache.js:174-179` `endsWithIndentedCode()` duplicates `src/split.js`'s own B7 guard with drift risk.** `split.js` (lines 108-116) already rejects any boundary whose settled prefix ends in indented code (B7), including CRLF-normalized handling (`.replace(/\r$/, "")` at split.js:115) before the 4-space test. `md-cache.js`'s copy (lines 174-179) re-implements the same last-line/4-space check but **omits the `\r` strip**: `settled.slice(lastNl + 1).replace(/\t/g, "   ")` vs split.js's `.replace(/\r$/, "").replace(/\t/g, "   ")`. I fuzzed 200k random small markdown-like strings through `splitSettled()` and could not find a case where the returned `settled` still ends in indented code (split.js's own B7 already filters it), so today this second check in md-cache.js is dead code in practice — `split.js` never returns a `settled` that would trip it. It is retained defensively ("defense in depth"), which is reasonable, but the `\r` omission is a real (if currently unreachable) drift point: if `split.js`'s B7 logic is ever loosened or a future code path calls `endsWithIndentedCode` on text `splitSettled` didn't produce, the two implementations would disagree on CRLF input. Recommend importing/reusing one indented-code-line predicate from `split.js` instead of maintaining a second, textually different copy.

**Confirmed hash duplication (Low severity, matches task's stated concern):**

**Config-vs-code duplication (documentation mirrors, not code duplication, but still a drift point):**

**No dead code found in exports:** every exported function in `src/md-cache.js`, `src/seg-cache.js`, `src/patch-state.js`, `src/stats.js`, `src/split.js` has at least one real (non-test) call site, confirmed by grep. No leftover old drift-guard functions or orphaned exports.

## 3. Inconsistencies

- **API return shapes are consistent end-to-end.** `install()` returns `{installed: boolean, adopted?: boolean, reason?: string}` identically in `md-cache.js` and `seg-cache.js`; `uninstall()` returns `{restored: boolean, reason?: string}` identically in both. `src/patch-state.js`'s `setupMd`/`setupSeg`/`teardownMd`/`teardownSeg` consume exactly these shapes (checked `res.installed`, `res.restored`, `res.reason`) and translate them into lifecycle states (`active`/`unsupported`/`ownership-lost`/`inactive`) without shape mismatches. `scripts/benchmark-worker.mjs` (lines 148, 156, 215-221) consumes the same `{installed}`/`{restored}` shapes directly (bypassing `patch-state.js`, calling `md-cache.js`/`seg-cache.js` install/uninstall itself) and checks `res.installed`/`result.restored` correctly — no shape drift between the two call paths (extension via patch-state.js vs. benchmark worker calling the cache modules directly).
- **`compatibility.json` is *not* consumed identically everywhere**, though not incorrectly: `scripts/check-upstream.mjs` reads `compat.versions[pi.version]`, `compat.implementationHashes[pi.version]` for diagnostic (non-gating) output. `extensions/index.ts`'s `loadAllowlistHashes()` reads `compat.implementationHashes` across *all* versions (flattened into one allowlist Set, `extensions/index.ts:36-46`) rather than keying off the currently-resolved pi version — this is intentional (any hash the package has ever validated is accepted, decoupling install-time compatibility from the exact resolved pi version at runtime), but it means `extensions/index.ts` and `scripts/check-upstream.mjs` read the same file with different selection semantics (all-versions-flattened vs. current-version-only). This is a legitimate design choice given the plan's "one compatibility unit" model but is worth naming explicitly as an asymmetry a future reader could trip on. `compat.versions.*.patches` and `compat.markdownThemeSignature`/`cacheBudgetCalibration` are read by none of the scripts (see §2) — so "consumed identically everywhere" doesn't hold for the file as a whole, only for the two fields (`versions[ver].piTui`, `implementationHashes`) that are actually wired up.
- **package.json scripts vs CI vs README are coherent**, with one intentional plan-vs-shipped gap: the plan (`/tmp/ado-plan-clean.md`, Task 7 / Checkpoint B section) references a `release:verify` script (`npm run release:verify -- --output .bench-results/release.json`) that does not exist in `package.json`, in any `scripts/*.mjs` file, or in `.github/workflows/ci.yml`. What *is* shipped is `release:feasibility` (`scripts/release-feasibility.mjs`, wired into `package.json:60` and referenced by the `quick-bench` CI job at `.github/workflows/ci.yml:47`), which implements the plan's Checkpoint B gate (tests + compat + premise + paired ±20 MiB RSS bound) but not the full Task 7 "controlled release validation" (20-block replay on the release platform + evidence promotion + pack check bundled into one command with a release-version argument). This looks like a deliberate, reasonable scope reduction (Task 7's `release:verify` is effectively performed today as a manual sequence: `npm run premise` → `node scripts/promote-evidence.mjs --release vX.Y.Z` → `npm run check-pack`, each independently documented in README/`docs/UPSTREAM_STATUS.md`), and README/CI never advertise a `release:verify` script that doesn't exist — so there is no user-facing broken promise. Still flagging because the plan names it as an acceptance criterion for Task 7/Checkpoint B and it is not present as a single executable command; a future contributor following the plan literally would look for `npm run release:verify` and not find it.
- **README/CI/package.json command names otherwise agree exactly**: `npm run compat`, `npm run compat:matrix`, `npm run verify`, `npm run premise`, `npm run test:perf`, `npm run check-pack`, `npm run release:feasibility` all appear with matching invocations across `package.json`, `.github/workflows/ci.yml`, and `README.md`/`docs/UPSTREAM_STATUS.md`. Test count claim in README ("83 tests") matches the live `node --test` output exactly.
- **`docs/PLAN.md`** (not part of this diff's changed-files set but present in the working tree) still contains a hard-coded `/Users/shamash/local/lib/node_modules/...` path (line 77), which would fail the plan's "No hard-coded developer path" acceptance criterion if this file were considered in scope. It is **not** shipped in the npm tarball (confirmed via `npm pack --dry-run --json`, `PLAN.md` absent from the file list) and is excluded from `tsconfig.json`'s type-check scope, so it has no functional or packaging impact — purely a residual internal planning artifact with a stale path reference. Not a code seam issue; noting only because the task's forbidden-reads list explicitly separates `docs/research/` from other docs and this file is adjacent.

**Blocking issues: none.** All tests pass (83/83), typecheck is clean, the exact package manifest matches, both compatibility fixtures (0.80.7, 0.82.1) install and validate cleanly in isolated roots, and a live 3-block benchmark smoke run completes correctly end-to-end with plausible byte-identical, ratio, and memory output. 4. Consider importing one shared "ends with indented code" predicate instead of maintaining a second, textually different (missing `\r` handling) copy in `src/md-cache.js` alongside `src/split.js`'s canonical B7 implementation.

**Maturity: 8/10.** The seams between scripts are unusually well-factored for a project this size (shared `benchmark-lib.mjs`/`resolve-pi.mjs`/`stats.js` genuinely eliminate the duplication risk the task was scoped to look for), API contracts are used consistently everywhere, and the verification pipeline (tests, typecheck, compat, compat:matrix, check-pack, premise, release-feasibility) all run cleanly today.
