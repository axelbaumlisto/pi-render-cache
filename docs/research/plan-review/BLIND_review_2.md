# Research: Blind factual and methodological review of `/tmp/pi-render-cache-plan-clean.md`

## Summary

**Verdict: revise before execution. Maturity: 7/10.** The upstream-status narrative is substantially accurate: `v0.82.1` is the latest release at the stated commit; current `main` differs only by changelog edits; issue #6665 remains open; #6792 was ultimately attributed by its reporter to an extension; and PRs #7017/#7082 were closed unmerged. The main deficiencies are scientific: the proposed benchmark and retirement gate do not define sampling, uncertainty, equivalence margins, or decision rules, and the proposed repeated probing of style callbacks cannot guarantee behavior-preserving fallback for stateful/side-effectful callbacks.

7. **UNVERIFIED — The plan’s local test counts and timing ranges are not externally attested (medium).** The claims `64/64`, `821–1031 ms vs 22–25 ms`, `1.6–1.9 s vs 0.49–0.75 s`, and `649 ms vs 314 ms` have no linked raw runs, machine-readable samples, harness revision, Node/OS/CPU metadata, or confidence intervals in the reviewed artifact. They may be true, but GitHub/web evidence cannot validate them. Treat them as preliminary measurements until Task 1 emits checked-in workload definitions plus archived raw output and environment metadata.

8. **REVISE — Benchmark comparisons are not scientifically adequate yet (high).** Fresh subprocesses and separate baseline/seg-only/md-only/both modes are good controls, but the plan omits warm-up policy, sample count, randomized/counterbalanced mode order, CPU affinity/power-state considerations, outlier policy, uncertainty intervals, and an explicit primary metric. “Best-of-N” is optimistically biased and unsuitable as the decision statistic; a soft `≥3×` threshold does not repair that bias. Measure distributions (preferably process CPU and wall time), use predeclared median or robust mean with bootstrap confidence intervals, keep identical chunk boundaries/cadence, randomize mode order by replicate, report all samples, and test interaction rather than informally attributing combined speedup to each cache.

9. **REVISE — The retirement gate is directionally sound but statistically undefined (high).** Requiring a released upstream version, extension-off/on comparisons, structural removal of each hot path, and ordinary/thinking/long-transcript workloads is appropriate. But “adds no statistically meaningful benefit” is not an adequate retirement criterion: failure to reject a difference is not evidence of equivalence. Predeclare per-patch practical-equivalence margins for CPU, latency/responsiveness, and memory; run paired, randomized replicates on at least representative platforms/Node versions; use an equivalence test or confidence interval wholly inside the margin; require correctness parity and no material regressions; and retire `md-cache` and `seg-cache` independently. Include a soak/interactive workload because microbench equivalence alone cannot establish user-visible retirement.

10. **REVISE — Callback probing cannot preserve original behavior for arbitrary stateful callbacks (high).** Task 3 proposes invoking `color` repeatedly to fingerprint/detect instability, then falling back to the original renderer on disagreement. Those probe invocations themselves can mutate callback state or produce side effects before the pristine render, so fallback is no longer behaviorally pristine. A throwing callback may also now throw during analysis at a different call count/time. Do not probe arbitrary user callbacks. Restrict support to callbacks with trusted identity/metadata supplied by pi, or require an explicit pure-style contract; otherwise fall back *without invoking the callback outside the upstream render*. This conflicts directly with Task 2’s requirement that stateful callbacks “preserve original behavior via fallback.” [upstream `DefaultTextStyle`](https://github.com/earendil-works/pi/blob/main/packages/tui/src/components/markdown.ts)

11. **REVISE — Compatibility checks should be behavioral, not only signature/shape checks (medium).** Structural assumptions can remain present while semantics change. In addition to source signatures, run a minimal differential canary against the resolved installed `pi-tui`: pristine versus each patch/mode across ANSI, Unicode, style, width, and invalidation cases. Report exact resolved package paths and hashes, since duplicate `pi-tui` instances can make version-only reporting misleading.

## Recommended acceptance changes

- Replace “best-of-N” with predeclared randomized replicates and distribution/CI reporting.
- Define the retirement gate as **paired equivalence**, per patch, with practical margins and correctness/memory constraints.
- Archive raw benchmark JSON with workload hash, commit/tag, resolved module paths, CPU/OS/Node, warm-up count, all samples, and mode order.
- Remove arbitrary callback probing; permit only explicitly trusted/pure style callbacks, otherwise pristine fallback without probes.
- Label the Context timing numbers “preliminary local observations” until reproduced by the new harness.

## Gaps / residual risks

- No independent execution of the package’s local tests or benchmarks was permitted by the blind-review scope; local timing claims remain unverified.
- GitHub evidence is a point-in-time snapshot (2026-07-25 API state shown by the sources); future `main` can invalidate it.
- Source inspection confirms the hot-path structure, not the exact percentage of end-to-end CPU attributable to each operation on every platform.
- The plan does not yet specify supported Node/OS/terminal matrix or an acceptable memory-overhead ceiling for caches.
